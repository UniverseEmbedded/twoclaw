## 为什么它不像“禁用/启用开关”

一个简单开关通常意味着：

* **对象自身**有一个状态（enabled/disabled）
* 谁来读都一样（全局一致）

而你这个负节点更像是：

* **在时间线上追加了一条“规则/补丁”**：从某个锚点开始，对某个主体，把一组历史节点从“可引用集合”里剔除
* 它必须带 **作用域**（至少：主体、分支、时间段），否则会把另一条世界线/另一个主体一起误伤。文档里把这条当成负节点的硬护栏之一：作用域要明确（主体/分支/时间段）。

## 落到实现：你其实在要一个“按主体的上下文投影”

最贴你描述的实现方式，是把系统拆成两层：

1. **Base history（客观发生过）**

* turn/scene DAG 仍然完整存在，不删、不改。

2. **View / Context projection（对某主体，本次拼接允许引用哪些）**

* 负节点是“规则条目”，在拼上下文时参与计算：

  * subject = A
  * branch = A 所在分支（或 fork 后某条分支）
  * effective_from = 某个 turn/scene（Y 形分叉点或其后）
  * targets = 要禁用的 turn/scene 集合或区间
  * mode = “不可见/不可引用/不可推理”（至少先做“不可引用”那条最稳路线也行）

这样同一段共享历史：

* 给主体 A 拼 history 时命中规则 → 过滤掉 targets
* 给主体 B 拼 history 时不命中规则 → 完整保留

**B. 你要做非常重的本地计算/音频/实时流媒体管线**

* 才会考虑 **C++**，但这条路工程成本最高、跨平台最麻烦
* 真到这一步，很多时候 **Rust（配合 Tauri command）** 比 C++ 更划算：同样是 native 性能，集成桌面端更顺

### 对你最现实的“折中推荐”

* **第一阶段：纯 TS（NextChat 内部）**
  先把“时间轴闭环”跑通：scene/turn/marker、分支、重跑、保存、导出
* **第二阶段：如果需要本地数据库/索引**
  优先用 **Tauri 的 Rust side** 做本地能力（SQLite/文件系统/索引任务队列），前端通过 Tauri command 调用
* **第三阶段：只有在你明确要 Python 生态**（解析/embedding/向量）
  再把 Python 服务接进来（HTTP/WebSocket），并接受打包复杂度

一句话：**别为了“以后可能要”先上 Python/C++ 后端**；你现在的瓶颈更可能是“数据模型与交互设计”，不是性能。

    if (!over || active.id === over.id) return;

    const oldIndex = items.findIndex((x) => x.id === active.id);
    const newIndex = items.findIndex((x) => x.id === over.id);
    if (oldIndex < 0 || newIndex < 0) return;

    updateItems(arrayMove(items, oldIndex, newIndex));
  };

  const addItem = () => {
    updateItems([...items, { id: uid(), text: `Turn ${items.length + 1}` }]);
  };

  const removeItem = (itemId: string) => {
    updateItems(items.filter((x) => x.id !== itemId));
  };

  return (
    <div
      className="rounded-xl border bg-[var(--node-bg,white)] shadow-sm"
      style={{
        width: 260,
        borderColor: selected ? "#FA5D19" : "rgba(0,0,0,0.12)",
      }}
    >
      {/* 关键：把“拖动节点”限制在标题栏 */}
      <div className="scene-drag-handle flex items-center justify-between gap-2 rounded-t-xl border-b px-3 py-2">
        <div className="text-sm font-semibold">{d.label || "Scene"}</div>
        <button
          className="nodrag rounded-md border px-2 py-1 text-xs"
          onClick={(e) => {
            e.stopPropagation();
            addItem();
          }}
          type="button"
          title="添加条目"
        >
          <Plus size={14} />
        </button>
      </div>

      {/* 列表区域：必须 nodrag，避免拖条目时拖走节点 */}
      <div className="nodrag space-y-2 px-3 py-3" onPointerDown={(e) => e.stopPropagation()}>
        <DndContext sensors={sensors} collisionDetection={closestCenter} onDragEnd={onDragEnd}>
          <SortableContext items={items.map((x) => x.id)} strategy={verticalListSortingStrategy}>
            {items.length === 0 ? (
              <div className="text-xs text-black/40">（暂无条目，点右上角 + 添加）</div>
            ) : (
              items.map((it) => <SortableRow key={it.id} item={it} onRemove={removeItem} />)
            )}
          </SortableContext>
        </DndContext>
      </div>

      {/* 你需要连线的话照样给 Handle */}
      <Handle type="target" position={Position.Top} />
      <Handle type="source" position={Position.Bottom} />

}

## 1) 标记只能放在节点前/后，还是二者都可以？

### 我建议：**二者都可以**，但要分清“锚点语义”

同一个标记在图上看起来像“贴在节点前/后”，但真正决定含义的是它的 **anchor（锚点）+ direction（作用方向）**：

* **后置标记（更常用）**：挂在某个 Scene/Turn **之后生效**

  * 语义：从这个节点之后，规则开始影响可见性/压缩/分歧
  * 很符合直觉：发生了某个事件后才失忆/才开始压缩
  * 对时间轴 UI 也最自然（像“从这里开始启用某规则”）

* **前置标记（必要但少用）**：挂在某个 Scene/Turn **之前生效**

  * 语义：在进入这个节点之前，你就已经处在某种规则状态（比如：进入这一幕前，A 就已经失忆/已经被压缩为某摘要）
  * 适合两类情况：

    1. **导入历史/中途接入**：你从某一幕开始才接入系统，但你想声明“前史对某主体无效/已压缩”
    2. **把规则当‘前置条件’**：比如“进入这幕前，必须忘掉某段记忆”这种门槛式叙事

> 关键点：**别让“前/后”变成两套完全不同的对象**。它们应该只是同一个 marker 的两个挂载位置，marker 本体一致。

### 更稳的模型：marker 不写“前/后”，而写

* `anchorNodeId`
* `effective = "AFTER" | "BEFORE"`
* （可选）`until = nodeId | null`（如果不是永久生效）

这样你在 UI 上既能呈现“前置/后置小挂件”，又不会让数据结构分裂。

## 2) 标记条目从节点上分离下来的话呢？

你说的“分离”我理解成两种不同层级的分离，我分别给建议。

### A) **UI 上分离（推荐）**：标记不挤在节点卡片里

这对你做“控制台”非常重要：如果把 marker 全塞进 scene 节点内部，节点会变成“万能垃圾桶”，地图会越来越像电路板。

推荐 UI 结构是：

* 地图上 Scene 节点只负责“叙事骨架”
* marker 用一种“贴边徽章/挂件”呈现（像 Git tag / annotation）
* 点击 marker 打开侧栏 Inspector（编辑作用域、目标、摘要内容、是否启用等）

这样视觉上仍然“贴着那个节点”，但信息密度不会压垮节点。

### B) **数据上分离（强烈推荐）**：marker 永远是独立对象

原因很现实：marker 往往需要：

* 指向多个 target（禁用一串 turn/scene）
* 有作用域（主体 A、不影响主体 B）
* 可能有版本、撤销、注释、作者
* 可能需要被复用/复制到别的分支

所以 marker 最好是独立实体，节点只是引用它：

* Node 上存 `markerRefs: [{markerId, attach:"BEFORE/AFTER"}]`
* Marker 表里存完整规则：`type/targets/scope/effective/until/payload...`

这样你做：

* “同一个 marker 挂在多个节点上”（比如同一个压缩摘要在多个分支共用）
* “移动 marker 生效点”
* “撤销 marker”
  都会非常干净。

# 放在前/后：三种路线的效果

**A. 只后置（AFTER）**

* **语义**：从某节点开始生效（更贴叙事直觉：“从这里开始失忆/压缩”）。
* **效果**：实现简单、用户好理解；时间轴浏览最顺。
* **代价**：不擅长表达“进入这一幕之前就已经处在某规则里”的前提条件（需要变通处理导入历史）。
* **适用**：先把 80% 场景跑通的 MVP。

**B. 只前置（BEFORE）**

* **语义**：进入某节点之前就要满足/执行规则（门槛式）。
* **效果**：适合“前史导入/入场要求”；时间轴上像“门栓”。
* **代价**：多数叙事修改其实发生在事件之后，用前置会别扭；用户可能误解“覆盖多远”的范围。
* **适用**：很小众，通常不单独采用。

**C. 前+后都支持（推荐的长期形态）**

* **语义**：同一类标记，支持 `effective = BEFORE | AFTER`。
* **效果**：表达力完整；能处理“导入前史”和“从此开始”的双场景。
* **代价**：实现要处理两个锚点的作用域与叠加顺序；测试量更大。
* **适用**：走向稳定产品时的目标形态。

# 是否分离：两条路线的效果

**1) 不分离（标记是节点属性/内嵌在节点里）**

* **能否分离**：短期最省事；后期可迁移，但需要数据迁移。
* **过程**：无（先用着）。
* **结果/影响**

  * ✅ 简单直观：看哪个节点就知道它“带着什么标记”。
  * ❌ 复用差：同一规则挂多处要复制粘贴；
  * ❌ 难审计/难撤销：规则分散在各节点里；
  * ❌ 不利分支：做 Y 形分叉（A 失忆、B 不失忆）时得复制两份节点属性，易串味。
* **适用**：纯单线剧情的小项目、快速原型。

**2) 分离（标记是独立实体，节点只挂“引用”/锚点）——推荐**

* **能否分离**：完全可行；这是“规则层”的正解。
* **过程（迁移步骤）**

  1. **定义 Marker 实体**：`id, type(NEGATE/COMPRESS…), anchorNodeId, effective(BEFORE/AFTER), scope(主体/分支), targets, payload, until(可选)`

* **结果/影响**

  * ✅ 可复用：同一标记可挂多处/多分支；
  * ✅ 可审计：独立时间线、作者、备注、撤销；
  * ✅ 易做主体/分支作用域：A 生效、B 不生效变成自然配置；
  * ✅ 易做批量操作（批量失效/批量改范围）；
  * ⚠️ 复杂度上升：需要“收集→排序→应用”的规则引擎；UI 也要有标记列表/搜索。
* **适用**：你这种“Y 形分叉、主体选择性失忆、上下文压缩”的叙事控制台。

# “分离”的可行性、过程、结果（更具体一点）

**可行性**：高。标记本质是“规则”，而规则天然就是独立于节点内容的东西。
**最小迁移过程**（一次性脚本 + 小改引擎）：

1. **Schema**：加 `markers[]` 顶级表；节点保留 `markerRefs[]`。
2. **数据迁移**：把每个节点里内联的 `{type, payload, scope}` 提升为单独 `marker`；设 `anchorNodeId=该节点`、`effective=AFTER`（前期全转 AFTER 最省事）。
3. **引擎**：构建上下文时：

  * 收集：`markers` 中满足 `scope` 且在路径上的（含 BEFORE/AFTER 判断与 `until` 截断）
  * 排序：按时间、effective（通常 BEFORE 先于该节点应用，再应用 AFTER）
  * 应用：NEGATE 过滤、COMPRESS 替换、FORK_MARK 仅做标识
4. **UI**：节点旁显示 chip；独立“标记面板”支持筛选（按主体/类型/有效区间）。

## 怎么样说才是对的（更精确的表述）

你提的 Y 形例子，正确说法应该是：

### 正确说法 1：不分离也可以做 A/B 不同效果，但必须“内联规则 + scope”

* **不分离（内联）**：节点里有 markers 列表，marker 自带 `scope`。

  * A 失忆：在分叉点后（或锚点处）加一条 marker：`scope=subject A`
  * B 不失忆：啥也不加（或 `scope=subject B` 不命中）
  * ✅ 不需要复制节点
  * ❌ 规则散落在各节点里，不好统一管理/复用/移动生效点/审计

### 正确说法 2：分离不是“减少标记数量”，而是“把差异控制在规则层”

* **分离（独立 marker 实体）**：marker 独立存储，节点只引用或用 anchor 指向。

  * A 失忆：创建 `markerA`（scope= A）
  * B 不失忆：不创建 B 的 marker（或者创建一个反向规则，视需求）
  * ✅ 同样不需要复制节点
  * ✅ 更容易批量管理、撤销、移动锚点、复用、做历史审计
  * 仍然可能出现“多条 marker”：当你确实有多条不同规则时（这很正常）

### 一句话总结

**分离 ≠ 不用复制标记**
分离的好处是：当你必须出现多条规则时，复制的是“小规则对象”，而不是复制“历史节点/scene/turn 本体”，而且这些规则更可控、更可追踪。

## 用你的 Y 形分叉例子，最“干净”的表达方式是什么？

假设共享历史是 `H`，分叉点是 `F`：

* **只需要一个 marker（A 失忆，B 不动）**
